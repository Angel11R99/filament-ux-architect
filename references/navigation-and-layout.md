# Navigation and layout

Navigation should help a user recognize where work belongs and how to return to context. Inspect existing panel configuration and verify supported options in the installed version.

## Information architecture

- Group resources by user workflow and responsibility, not simply model names.
- Use navigation groups or clusters when they reduce a long or ambiguous menu; confirm the feature exists in the installed version.
- Use a dedicated resource page when record lifecycle maps cleanly to standard resource pages. Use a custom page when the task has a distinct workspace or flow.
- Keep related content together, but separate unrelated concepts rather than creating broad, nested tab systems.

## Page composition

- Put primary task and context first. Keep critical identifiers, status, and actions visible where users need them.
- Use sections, grids, flex layouts, fieldsets, split layouts, tabs, and collapsible sections only when their grouping or space use improves comprehension.
- Reserve collapsible areas for secondary or optional information; do not hide critical state.
- Use tabs for a small number of related, distinct groups. Avoid nested tabs, excessive tab counts, and horizontal scrolling.
- Provide purposeful empty states with an explanation and relevant next action.

## Responsive and accessible behavior

- Test hierarchy and task completion at narrow widths, not merely whether the page fits.
- Avoid overly wide forms and tables; recompose information or provide focused detail views.
- Preserve keyboard focus order, visible focus, clear labels, error announcements, adequate contrast, and accessible action names.
- Follow the project's theme, typography, spacing, icon, and localization conventions.
